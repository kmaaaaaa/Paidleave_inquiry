## 1. リリース概要

Slack `@oyasumi_inquiry` Bot は、これまで**人間ユーザーが直接メンションした場合のみ**応答する実装だった。`app_mention` イベントは Slack 仕様上、**他のアプリ/Bot 発のメンションでは発火しない**ため、Workflow Builder 等からの自動呼び出しが機能しなかった。

本リリースで `message.channels` イベントを新規購読し、アプリ経由メンションにも応答できるようにした。既存の `app_mention` フローは温存し、後方互換を維持している。

### 採用した仕様: 案 B

| ケース | 挙動 |
|---|---|
| 人間が直接メンション（既存） | 既存どおり応答 |
| Workflow Builder 等で `event.user` が入る投稿からメンション | **実行者の有給残日数を返す** |
| 他のBot/App が純粋にメンション（`event.user` なし） | **無応答** |
| 自 Bot の投稿 | **無応答**（無限ループ防止） |

案 B を選んだ理由: プライバシー影響最小。「誰でも任意の人の残日数を照会できる」案 C は不採用。

## 3. 追加された関数

### `Code.gs`
- `isMessageProcessed(channel, ts)`: 補助キャッシュによる処理済み判定（キー: `msg_{channel}_{ts}`、TTL: 600 秒）
- `markMessageProcessed(channel, ts)`: 補助キャッシュへの記録

### `SlackHandler.gs`
- `handleChannelMessage(event)`: `message.channels` イベントを案 B 仕様で処理
- `isOwnBotMessage(event, config)`: 自 Bot/自 App 発の投稿を 3 条件 OR で判定
  1. `event.user === config.BOT_USER_ID`
  2. `event.bot_id === config.OUR_BOT_ID`
  3. `event.subtype === 'bot_message' && event.bot_profile?.app_id === config.OUR_APP_ID`
- `extractMentionedBotUserId(text, botUserId)`: `<@BOT_USER_ID>` / `<@BOT_USER_ID|displayname>` を検出

### `Config.gs`
- `printBotIdentity()`: `auth.test` API を呼んで `user_id` / `bot_id` をログ出力（Script Properties 初期設定用）
- `setConfig()`: 冒頭に `throw new Error(...)` ガード追加（誤実行時の Script Properties 破壊防止）

### `Test.gs`
- `testIsOwnBotMessage`
- `testExtractMention`
- `testHandleChannelMessageSkipOwnBot`
- `testHandleChannelMessageBotSenderIgnored`
- `testHandleChannelMessageWorkflowUser`
- `testDuplicateMessageCache`

## 7. トラブルシューティング

### メンションしても返信が来ない

**診断フロー**:

1. **Apps Script Editor → 実行数** で `doPost` が呼ばれているか確認
   - 呼ばれていない → Slack → GAS の経路に問題（URL 不一致 / Event Subscription 未設定 / ワークスペース未インストール）
   - 呼ばれてエラー終了 → ログを確認
   - 呼ばれて完了しているが無応答 → 下記 2 以降

2. **`printBotIdentity` を実行**
   - `"ok": true` → Bot Token は有効
   - `invalid_auth` / `token_expired` → Bot Token が無効化（再インストール時に変わった可能性）。Slack App → OAuth & Permissions から新トークンをコピーし `SLACK_BOT_TOKEN` を更新

3. **`testFindPaidLeaveBalance` を実行**
   - `Found user: ...` → スプレッドシート検索は正常 → Script Properties の `BOT_USER_ID` 等を再確認
   - `User not found: U02JLA69B1N` → **スプレッドシート C 列のデータ問題**（下記「C 列データ問題」参照）
   - `Sheet not found` → `SHEET_NAME` プロパティが誤っている
   - 例外発生 → SPREADSHEET_ID / 共有権限を確認

### 全ユーザーに「対象外」が返される（C 列データ問題）

C 列（userid_slack）の値が取得できていない可能性。実際に 2026-04-22 に発生。

1. [有給管理表スプレッドシート](https://docs.google.com/spreadsheets/d/1HpeLLzMprhRCKX1Xc_9FjjAOEODEYl4-ISSQh3pHGWs/edit) を開く
2. C 列のデータセルをクリックし、数式バーを確認
   - `#N/A` / `#REF!` / 空 → **Notion 同期（本プロジェクト外）の失敗が原因**。Notion 同期側の復旧が必要
   - 素のテキスト（`Uxxx`）で表示されている → 値がユーザーの Slack User ID と一致するか確認

> **重要**: 本プロジェクト（Paidleave_inquiry）は C 列の User ID データを生成していない。C 列は別スクリプトの Notion 同期が書き込む設計のため、`#N/A` が返る事象はこのプロジェクトでは修正できない（Notion 同期側の範囲）

### 無限ループ / 同じ応答が何度も投稿される

- `BOT_USER_ID` / `OUR_BOT_ID` / `OUR_APP_ID` が Script Properties に正しく登録されているか確認
- `isOwnBotMessage` の 3 条件でフィルタされるため、上記 3 項目の不足は無限ループの引き金になり得る

## 8. 本セッション中のインシデント

### インシデント 1: `setConfig` 誤実行による Script Properties 破壊

**発生**: Phase 4 デプロイ後、原因特定のため `setConfig` を実行したと思われるタイミングで、Script Properties 7 項目が全てダミー値（`'xoxb-your-bot-token-here'` 等）で上書きされる事故が発生。

**原因**: `setConfig()` はテンプレート関数として `setProperties({...ダミー値})` を実行する構造になっていた。Apps Script Editor の関数ドロップダウンから誤実行されるとリスクが顕在化する設計だった。Opus DA では「低リスク」判定で本リリーススコープ外としていたが、実害に至った。

**対応**:
- 即座に `setConfig()` 先頭に `throw new Error('setConfig は誤実行防止のため停止中。値を編集し、この throw 行をコメントアウトしてから実行してください。')` を追加（今回のリリースに含む）
- Script Properties は手動で復旧

**教訓**:
- DA 重要度「低」でも、**実行コンテキストが破壊的**な関数（`setProperties` / `deleteAll` 系）は優先的にガードを入れるべきだった
- テンプレート関数でも「本番設定を破壊しうる」ものは `throw` ガードをデフォルトとする

### インシデント 2: Slack Bot Token のチャット露出

**発生**: インシデント 1 の復旧過程で、Slack Bot Token をチャット上で共有する必要が生じ、トークンが会話履歴に残った。

**対応（ユーザー側で実施推奨）**:
- Slack App → OAuth & Permissions → **Reinstall to Workspace** で新トークンを発行
- `SLACK_BOT_TOKEN` を新トークンに差し替え
- 旧トークンは無効化される

## 9. Out of Scope / 既知の制約

本リリースには**含めていない**。別 Issue / 別 PR で管理する。

### OOS-1: Slack 署名検証（HMAC）の未実装

- 現状、`SLACK_SIGNING_SECRET` を Script Properties に保持しているが、`X-Slack-Signature` / `X-Slack-Request-Timestamp` による HMAC 検証コードは未実装
- `message.channels` 購読で `doPost` への到達量が増え、なりすまし POST への耐性が実質的に重要化する
- GAS `doPost(e)` では `e.parameter` でヘッダを取得できないため、実装には中継サーバー経由など追加設計が必要
- 推奨: 別 PR で ADR 起票 → 実装検討

### OOS-2: 既存 `X-Slack-Retry-Num` 検出ロジックの実効性欠如

- `Code.gs` の `e.parameter['X-Slack-Retry-Num']` 分岐は GAS の `e.parameter` が HTTP ヘッダを含まないため実効性なし
- 現状の重複防止は `event_id` キャッシュ + 本リリースで追加した `channel+ts` 補助キャッシュで実用上十分機能している
- 害はないため残置、別 Issue で削除 or 置換を検討

### データ依存: C 列の Notion 同期

- 有給管理表 C 列（userid_slack）は本プロジェクト外の Notion 同期スクリプトが書き込む設計
- Notion 同期が失敗すると C 列に `#N/A` が残り、Bot 側では全ユーザー「対象外」応答になる
- Bot 側での対処は不可。Notion 同期側の監視・復旧が別途必要
